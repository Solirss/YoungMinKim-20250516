## 서비스 개요

### 풀고 싶었던 문제

생필품을 살 때 사람들은 "이 가격이 진짜 싼 건가?"를 알아내려고 여러 앱을 왔다 갔다 합니다. 가격 비교, 리뷰, 단가 계산, 다 직접 해야 해요. 단돈 몇천 원 아끼려고 시간을 너무 많이 씁니다.

이걸 **숫자 배지 하나**로 압축해서, 유저가 0.1초 안에 "사도 되겠다"는 확신을 갖게 해주는 게 이 프로젝트의 목표입니다.


### 동작 흐름

```
1. 유저가 카테고리 클릭 또는 검색
        ↓
2. 다나와 크롤링 (실패하면 목 데이터로 폴백)
        ↓
3. 클릭 행동에서 성향 신호 추출 → brand / volume / mixed 판별
        ↓
4. GPT-4o-mini가 성향에 맞춰 0~99점 매김 (실패 시 직관적 합산 알고리즘 폴백)
        ↓
5. 상품 카드에 점수 배지 + 25자 툴팁 표시
```

## 핵심 구현 상세

### 1. 다나와 크롤링

**다나와를 선택한 이유:**
- 정적 HTML 렌더링 구조라 `axios + cheerio` 크롤링이 안정적
- 쿠팡(SPA 구조), 네이버 쇼핑(JS 렌더링) 모두 정적 크롤링이 불안정함을 확인 후 전환
- 여러 쇼핑몰 최저가를 한 번에 비교 제공해 시장 평균 단가 계산에 유리
- 별도 API 키 불필요

**크롤링 항목:**

| 필드 | 다나와 선택자 | 비고 |
|---|---|---|
| `name` | `.prod_name a` | 상품명 |
| `price` | `.price_sect a strong` | 최저가, 숫자만 추출 |
| `image` | `.thumb_wrap img[src]` | 프로토콜-상대 URL 보정 |
| `brand` | `.prod_name .prod_eng_name` | 없는 경우 빈 문자열 |
| `rating` | `.text__score` | 평점 (예: 4.65) |
| `reviews` | `.text__review .text__number` | 리뷰 수 (999+ 는 999로 표시됨) |
| `volume` | 상품명 정규식 파싱 | `(\d+)\s*(kg\|g\|ml\|L\|매\|롤...)` |

> **선택자 디버깅 메모**: 처음에는 옛 구조(`.star_rating[data-rating]`, `.cnt_opinion`)를 가정했는데 결과가 계속 0이 나왔어요. "다나와는 JS로 평점을 동적 로드하는 거구나" 하고 잘못된 결론을 내리고 다른 라이브러리들을 검토했지만, `curl`로 raw HTML을 직접 받아 grep해보니 평점·리뷰가 처음부터 정적 HTML에 있었습니다. 다나와가 클래스명을 바꿨던 것뿐이었어요. 자세한 회고는 [설계 고민 요소 0번](#0-가정-검증의-중요성--다나와-평점-수집-디버깅-기록)에 정리.

**크롤링 실패 시 폴백:**

```
크롤링 결과 3개 미만
    → resolveMockCategory() 로 키워드→카테고리 매핑
    → MOCK_DATA[category] 목 데이터 반환
```

**크롤링 후 시장 기준선 계산:**

같은 검색 결과 안의 상품들끼리 비교해서 "이 카테고리의 시장 평균"을 정의합니다.

```js
avgPrice         = 전체 상품 평균가
avgPricePerUnit  = pricePerUnit이 있는 상품들의 평균 단가
                   (단가 파싱 실패 상품은 평균에서 제외)

// 각 상품에 플래그 부여
isPremium = price > avgPrice * 1.3   // 시장 평균의 130% 이상이면 프리미엄
```

또 90일 가격 시뮬레이션을 상품마다 다른 시나리오로 생성합니다:

```js
trend       = 랜덤 -15% ~ +15%      // 떨어지는/안정/오르는 추세
noiseLevel  = 랜덤 3% ~ 11%         // 일별 변동 강도
discount    = 15% 확률로 -5~15%     // 가끔 할인 이벤트 점프
```

상품마다 추세·변동성·이벤트 점프가 다르게 나와서 차트 모양이 다양하고, 가격 타이밍 점수에도 변별력이 생깁니다. 실서비스에서는 이 시뮬레이션을 DB에 쌓인 실제 가격 이력으로 교체해야 해요.

### 2. 성향 판별 알고리즘

유저가 상품을 클릭할 때마다 5가지 신호를 실시간으로 수집합니다.
같은 상품의 같은 신호는 `"productId:signalType"` 키로 중복을 방지합니다 (예: `"danawa-0-123:bulk"`).

**신호 가중치 체계:**

```
[브랜드파 신호]
  +2  동일 브랜드 반복 클릭 (같은 브랜드 상품을 2회 이상 클릭한 브랜드 수)
  +2  프리미엄 상품 클릭   (시장 평균가 130% 이상인 상품 클릭)
  +2  고평점 상품 클릭     (평점 4.7 이상 — 브랜드 신뢰도 직접 신호)
  +1  평균가 이상 상품 클릭 (보조 신호: brand 필드 비었을 때 보완)

[용량파 신호]
  +1  대용량 상품 클릭     (isBulk 상품. 가중치 낮은 이유: 다나와 대부분 대용량)
  +2  저단가 상품 클릭     (시장 평균 단가의 80% 이하 상품)
```

**성향 판별:**

```
totalClicks < 3    →  "unknown" (Cold Start. 가중치 합이 아닌 실제 클릭 수 기준)
brandRatio >= 0.6  →  "brand"   (브랜드 가치파)
brandRatio <= 0.4  →  "volume"  (실속 용량파)
그 외              →  "mixed"   (복합 분석)
```

### 3. GPT 가성비 점수 산출

성향별로 완전히 다른 평가 기준 프롬프트를 구성해 GPT-4o-mini에 전달합니다.

**성향별 평가 기준:**

| 성향 | 핵심 기준 | 보조 기준 |
|---|---|---|
| brand | 가격 타이밍: 현재가 vs 3달 최저가 | isPremium 여부, 선호 브랜드 일치 여부 |
| volume | 단위당 단가 vs 시장 평균 | isBulk 여부 (대용량 가점) |
| mixed | 가격 타이밍(30%) + 단위 단가(30%) | 브랜드 신뢰도(20%) + 종합 가성비(20%) |

**GPT에 전달하는 상품 데이터 (토큰 절약을 위해 핵심만):**

**Example**
```json
{
  "index": 0,
  "name": "피죤 울트라 세탁세제 3kg",
  "brand": "피죤",
  "price": 12900,
  "pricePerUnit": 4,
  "unit": "g",
  "rating": 4.7,
  "reviews": 12043,
  "minPrice3M": 11500,
  "maxPrice3M": 14200,
  "marketAvgPrice": 14833,
  "marketAvgPricePerUnit": 5,
  "isPremium": false,
  "isBulk": true
}
```

**프롬프트 제약 조건 (점수 쏠림 방지):**

GPT는 기본적으로 긍정 편향이 있어서 자유롭게 두면 대부분 80~95점에 몰립니다. 그래서 명시적으로 분포 가이드를 박아넣었어요.

```
- 0~99점 범위 사용
- 상품 간 점수 차이 최소 5점 이상 (전부 95점대 절대 금지)
- 진짜 가성비 좋은 상품 1~2개만 80점 이상
- 가격이 3달 최고가에 가까운 상품 → 35점 이하 가능
- 시장 평균보다 단가 비싼 상품 → 45점 이하
- 점수 분포 예시: 12, 28, 45, 61, 74, 88
```

**GPT 응답 형식:**

```json
{"scores":[{"index":0,"score":74,"tooltip":"최저가 대비 3% · 리뷰 1.2만개"}]}
```

- `temperature: 0.3` — 동일 입력에 점수가 크게 달라지지 않도록 낮게 설정
- `max_tokens: 900` — 상품 10개 기준 여유 있는 상한

### 4. Cold Start 처리

> **"엉성한 점수로 첫인상을 망치는 것보다 숨기는 편이 낫다"**

`totalClicks < 3`이면(클릭 데이터가 너무 적으면):
- 상품 카드 배지 → `🔒 점수 대기중`
- 헤더 PersonaBadge → `성향 분석 중 (N/3)`
- GPT 호출 자체를 안 함 (`scoreSource: "none"`)

신호가 약한데 점수를 억지로 매기면 유저가 "이 점수 못 믿겠는데?"라는 첫인상을 갖게 되고, 그 인상은 한 번 박히면 회복이 어려워요. 그래서 차라리 침묵하는 쪽을 택했습니다.

### 5. GPT 폴백 — 직관적 합산 알고리즘

GPT API가 실패하는 케이스(API 키 미설정 / 잔액 부족 / Rate limit / JSON 파싱 실패 / 네트워크 타임아웃)에는 자체 점수 산식으로 자동 폴백합니다.

**설계 원칙: "누가 봐도 점수 분해가 가능하게."**

이전에 만든 폴백 알고리즘은 가중치 비율 + 보너스 + 추세 보정 등이 섞여 있어서 "왜 이 점수?"에 답하기 어려웠어요. 결국 자신 있게 운영에 못 넣고 폴백을 통째로 빼버렸는데, 이번엔 단순 합산 방식으로 재설계했습니다.

**3개 항목, 각 0~33점, 합산 후 99로 cap:**

```
최종 점수 = 평점 점수 + 리뷰 점수 + 가격 점수   → 99로 cap
```

| 항목 | 만점 | 산식 |
|---|---|---|
| **평점 점수** | 33 | `(rating - 4.0) × 33` (4.0 → 0점, 5.0 → 33점) |
| **리뷰 점수** | 33 | `log10(reviews + 1) / 4 × 33` (100개 ≈ 16점, 1만 → 33점) |
| **가격 점수** | 33 | 성향별 기준 다름 (아래) |

**가격 점수 — 성향별 기준:**

| 성향 | 기준 | 만점 조건 |
|---|---|---|
| brand | 3개월 최저가에 얼마나 가까운가 | 현재가 = 최저가일 때 33점 |
| volume | 시장 평균 단가 대비 단가 비율 | 평균의 절반 이하면 33점 |
| mixed | 시장 평균가 대비 현재가 비율 | 평균보다 30% 저렴하면 33점 |

**계산 예시 — 신라면 멀티팩 (brand 성향)**

```
평점 4.9 → ratingScore = (4.9 - 4.0) × 33 = 30점
리뷰 28,341 → reviewScore = log10(28342)/4 × 33 ≈ 33점 (cap)
현재가 17,900 / 3달 최저 16,500 / 최고 19,800
  position = (17900 - 16500) / 3300 = 0.42
  timingScore = (1 - 0.42) × 33 = 19점

최종 = 30 + 33 + 19 = 82점
```

**툴팁 — 사람 친화적 분해 표시**

점수를 그대로 보여주지 않고, 유저가 이해할 수 있는 단위로 변환해 노출합니다.

| 성향 | 툴팁 예시 |
|---|---|
| brand | `3달 최저가 · 평점 4.7 · 리뷰 1.2만` |
| volume | `단가 35% 저렴 · 평점 4.6 · 리뷰 8.7천` |
| mixed | `평균보다 12% 저렴 · 평점 4.7 · 리뷰 9.8천` |

**`scoreSource` 값:**

- `"gpt"` — GPT-4o-mini 정상 응답
- `"local"` — GPT 실패, 위 합산 알고리즘으로 산출
- `"none"` — Cold Start (애초에 GPT 호출 안 함)

GPT 점수와 로컬 점수의 절대값은 다르지만, **변별력 방향(어떤 상품이 좋은가)은 일치**하도록 설계했어요. 결국 같은 상위 상품이 어느 경로로든 위로 올라옵니다.

## 설계 의도

### "AI가 쓴 추천 글을 유저가 또 읽게 하지 않는다"

GPT 역할을 **점수 계산기**로만 한정했어요. 유저에게 노출하는 건 숫자 배지 + 25자 툴팁이 전부.

GPT가 쓴 문장을 그대로 보여주는 방식은 기존 AI 추천이 이미 하고 있는데, 그게 잘 안 먹히는 이유는 "또 텍스트를 읽어야" 하기 때문이거든요. 텍스트 추천 → 텍스트로 답 → 또 읽기, 이 사이클을 끊고 싶었어요.

### 카테고리가 아니라 유저 자체를 분석

성향을 카테고리별로 따로 추적하지 않고, 전체 쇼핑 행동을 글로벌하게 누적합니다. 같은 유저가 세제에서는 브랜드파처럼, 쌀에서는 용량파처럼 행동해도 그 모든 신호가 합쳐져서 한 명의 "성향"으로 정의돼요. 시간이 지나면 성향이 자연스럽게 변할 수도 있고요.

### 알고리즘과 GPT의 역할 분리

키워드 → 카테고리 매핑 같은 단순 로직은 알고리즘으로, 맥락 이해가 필요한 점수 산출은 GPT로. 두 역할을 분리해야 GPT 비용을 줄이면서도 유연성을 유지할 수 있어요.

## 아쉬운 점 / 개선 여지

1. **실시간 가격 히스토리**: 현재는 시뮬레이션 데이터. 실 서비스에서는 스케줄러로 주기적 크롤링 후 DB 적재 필요
2. **다나와 크롤링 안정성**: HTML 구조 변경 시 CSS 선택자가 깨질 수 있음. 지속적인 모니터링 필요
3. **리뷰 수 표시 한도**: 다나와는 999개 이상의 리뷰를 "999+"로 표시해 999로 클리핑됨. 정확한 리뷰 수는 상품 상세 페이지 추가 크롤링 또는 별도 API 호출이 필요
4. **유저 로그 영속성**: 현재 클라이언트 메모리에만 존재해 새로고침 시 초기화됨. 실 서비스에서는 로그인 연동 + DB 저장 필요
5. **성향 타입 확장**: 현재 3가지(brand/volume/mixed). "시간 절약파", "친환경파" 등 다축 클러스터링 가능
6. **온보딩 성향 테스트**: Cold Start를 앞당기기 위해 신규 유저 대상 간단한 퀴즈("브랜드가 중요한가요, 용량이 중요한가요?") 도입 검토
7. **카테고리 8개 제한**: 현재 생활용품 4종(세제/휴지/기저귀/키친타올) + 음식 4종(쌀/라면/생수/김) 목 데이터 보유. 실서비스로 가려면 동적 카테고리 확장 구조 필요

## 설계 고민 요소 (미해결 과제)

MVP를 만들면서 명확한 답을 내리지 못한 구조적 고민입니다.

### 0. 가정 검증의 중요성 — 다나와 평점 수집 디버깅 기록

이 프로젝트에서 가장 큰 교훈은 **"검증 없이 추측으로 의사결정을 하면 알고리즘 전체가 잘못된 전제 위에 설계된다"** 였습니다.

**상황:**

초기 구현 시 다나와 옛 구조를 가정한 선택자(`.star_rating[data-rating]`, `.cnt_opinion`)를 사용했고, 결과가 항상 `0`이 나왔습니다. 여기서 "다나와는 평점을 JS로 동적 로드하니까 정적 크롤링으로는 수집 불가능하다"고 **추측만으로** 결론을 내렸습니다.

**잘못된 의사결정의 연쇄:**

1. 백엔드 `scorer.js`에서 `highRatingClicks` 신호를 사실상 무력화
2. 이를 보완하기 위해 `avgAboveClicks` 가중치를 +1 → +2로 강화
3. README에 "다나와 평점 수집 불가, 알고리즘으로 우회" 명시
4. 더 나아가 `puppeteer`, `Crawlee`, `Playwright`, `ScraperAPI` 등 **여러 라이브러리 대안을 진지하게 검토**

**진짜 원인 발견:**

`curl`로 다나와 raw HTML을 직접 받아 `grep`으로 분석한 결과:

```bash
$ grep -c "text__score" danawa_raw.html
44   # 한 페이지에 평점 데이터 44개

$ grep -oE 'text__score">[0-9.]+' danawa_raw.html | head
text__score">4.65
text__score">4.92
text__score">4.72
...
```

평점은 처음부터 정적 HTML에 포함되어 있었고, **단지 다나와가 HTML 구조를 새 클래스명(`text__score`, `text__review .text__number`)으로 변경했을 뿐**이었습니다. 선택자 두 줄 교체로 끝나는 문제였습니다.

**검토했던 라이브러리 대안 (불필요했던 것들):**

| 옵션 | 검토 시 가정한 강점 | 실제 |
|---|---|---|
| `js-crawler` | JS 실행 가능할 줄 | 동일 한계 + 2018년 이후 유지보수 중단 |
| `scrapy` | 강력한 크롤링 프레임워크 | Python이라 과제 제약 위반 |
| `Crawlee + Playwright` | JS 렌더링 가능 | Chromium ~300MB → Render 무료 메모리 한계로 배포 실패 가능 |
| `puppeteer` 직접 | JS 실행 가능 | 동일한 메모리 문제 |
| ScraperAPI | 외부 렌더링 서비스 | 진짜 필요하다면 한 줄로 가능했지만 — 그럴 필요가 없었음 |
| 네이버 쇼핑 API | 데이터 소스 전환 | 데이터 종류가 다르고, 다나와로 충분 |

**얻은 교훈:**

> "동작이 이상하면 라이브러리를 의심하기 전에 raw 데이터부터 확인하라."

> **"AI가 '안 된다'고 단정해도, 직접 raw 데이터를 받아 검증하라."**

이번 경우 AI 어시스턴트(Claude)도 처음에 "다나와는 JS로 평점을 동적 로드해서 정적 크롤링으로는 불가능하다"고 4번에 걸쳐 단언했습니다. 저는 그 답변을 그대로 받아들여 알고리즘을 우회 설계했고, 라이브러리 대안(`puppeteer`, `Crawlee`, `ScraperAPI` 등)까지 진지하게 검토했습니다. 하지만 "정말 100%냐"고 한 번 더 의심하고 `curl`로 raw HTML을 받아 `grep`했을 때, 평점이 처음부터 정적 HTML에 들어있다는 사실이 드러났습니다.

`curl` + `grep` 5분이면 끝났을 검증을 며칠 미룬 셈입니다. AI가 자신감 있게 답한다고 해서 검증 단계를 건너뛰면, 잘못된 전제 위에 알고리즘 전체가 설계됩니다. 면접에서 가져갈 가장 가치 있는 교훈은 새로운 기술이 아니라 **"AI 답변도 raw 데이터로 검증한다"는 디버깅 습관**입니다.

**그 이후 적용:**

- `crawler.js` 선택자 교체 → 평점·리뷰 모두 정상 수집
- `scorer.js`와 `App.js`에서 `highRatingClicks` 신호 복원, `avgAboveClicks`는 보조 신호(+1)로 재조정
- GPT 프롬프트에 `rating`/`reviews` 다시 포함시켜 점수 산출 정확도 향상

### 1. GPT에 점수를 위임하는 게 맞는가, 자체 알고리즘이 맞는가

| 항목 | GPT | 자체 알고리즘 |
|---|---|---|
| 맥락 이해 | 상품명, 브랜드, 가격 범위를 종합 판단 가능 | 명시적으로 정의한 변수만 반영 |
| 일관성 | 동일 입력에도 결과가 달라질 수 있음 | 항상 동일한 결과 보장 |
| 비용/속도 | 요청당 API 비용 + 레이턴시 발생 | 무료, 즉시 계산 |
| 설명 가능성 | 프롬프트로 조정 가능하나 블랙박스 | 수식이 투명해 디버깅 용이 |
| 확장성 | 파라미터 추가 시 프롬프트 수정만으로 반영 가능 | 수식 재설계 필요 |

**결론**: 초기에는 GPT로 빠르게 검증하고, 유저 데이터가 쌓이면 자체 알고리즘 + ML로 전환하는 것이 맞다고 봅니다.
지금 단계에서 알고리즘을 정교하게 만들어봤자 실제 유저 데이터 없이는 가중치를 검증할 방법이 없기 때문입니다.

### 2. 가성비 점수에 반영되지 못한 파라미터들

현재 점수에 반영된 파라미터는 가격 타이밍, 단위 단가, 평점, 리뷰 수 4가지입니다.
실제 가성비에는 훨씬 많은 변수가 관여합니다:

- 계절/시기 요인 (명절 전후 가격 급등)
- 행사 주기 (쿠팡 로켓와우 특가, 네이버 장보기 할인 주기)
- 대체재 존재 여부 (유사 성분/스펙 상품과의 비교)
- 재구매율 / 반품율 (실제 만족도 지표)
- 유통기한/소비 주기 (쌀 20kg은 가성비가 좋아도 혼자 사는 사람에겐 의미 없음)

이를 수식으로 모두 정의하기보다 **실제 구매 전환 데이터를 레이블로 ML 모델을 학습**시키는 것이 현실적입니다.
다만 이는 상당한 양의 유저 행동 데이터가 쌓인 이후의 과제입니다.

### 3. 카테고리별 가성비 지수 vs 데이터 요구량 트레이드오프

기저귀의 가성비와 쌀의 가성비는 완전히 다른 기준으로 평가되어야 합니다.
기저귀는 피부 안전성과 브랜드 신뢰도가 핵심이고, 쌀은 원산지와 단위 단가가 핵심입니다.
카테고리별로 다른 가중치 체계를 적용하면 정확도가 크게 올라가지만, 카테고리 수만큼 학습 데이터와 모델 관리 비용도 늘어납니다.

현실적인 타협안으로 **대분류 2개(식료품 / 생활용품)로 먼저 나누는 방향**을 검토하고 있습니다.

```
식료품   → 원산지, 유통기한, 단위 중량당 가격, 브랜드 신뢰도 가중치 높임
생활용품 → 용량 대비 단가, 성분 동등성, 가격 변동성 가중치 높임
```

이렇게 하면 카테고리별 완전 분리보다 데이터 요구량을 대폭 줄이면서도
"기저귀와 쌀을 같은 기준으로 평가하는" 문제를 해결할 수 있습니다.
단, 대분류 내에서도 편차가 크기 때문에 이 역시 완전한 해결책은 아닙니다.

### 4. "가성비 점수"인가, "AI 추천"인가

지금의 점수 산출 로직을 다시 들여다보면, 유저 개인의 취향에 맞는 상품을 골라주는 것에 더 가깝습니다. 브랜드 가치파에게는 "이 가격대에서 당신이 좋아할 만한 상품", 용량파에게는 "당신이 평소 찾는 단가의 상품"을 상위로 끌어올리는 구조이기 때문입니다. 엄밀히 따지면 "객관적 가성비"보다는 **"개인화 추천 적합도"**에 가깝습니다.

그렇다면 이 지표를 그대로 "가성비 점수"라고 부르는 것이 맞을까요, 아니면 "AI 추천 점수"로 바꾸는 것이 더 정확할까요?

**"가성비"로 유지하자는 입장:**
- 올웨이즈의 핵심 타겟인 35~50대 여성 유저에게 "가성비"라는 단어는 즉각적인 맥락을 전달합니다. "AI 추천"은 추상적이고 신뢰감이 덜 형성됩니다.
- 유저가 실제로 알고 싶은 것은 "이거 사도 후회 안 할까?"인데, 이 질문에 가장 직관적으로 답하는 단어가 "가성비"입니다.
- 점수 산출 기준에 가격 타이밍, 단위 단가, 시장 평균 대비 위치 등 객관적 가격 지표가 분명히 포함되어 있어 단순한 추천과는 다릅니다.

**"AI 추천"으로 바꿔야 한다는 입장:**
- 같은 상품이라도 유저 성향에 따라 점수가 달라지는 시점에서 이미 "객관적 가성비"는 아닙니다. 단어와 실제 동작의 괴리는 장기적으로 신뢰를 깎습니다.
- "AI 추천"으로 명명하면 점수가 다른 이유를 자연스럽게 설명할 수 있습니다 ("당신을 위한 추천이라 점수가 다릅니다").

**현재 결론:**
"가성비"라는 단어가 가지는 즉각적 인지 효과를 포기하기 어려우므로 **명칭은 "가성비 점수"로 유지하되, 툴팁과 성향 배너에서 "당신의 쇼핑 패턴 기반"임을 명시**하는 절충안을 채택했습니다. 다만 이는 마케팅적 결정에 가깝고, 유저 인터뷰나 A/B 테스트로 "AI 추천 점수" 버전과 비교 검증할 가치가 있습니다.
